# 项目初始化：知识沉淀规则注入项目 AGENTS.md

> 背景：开工调研/任务后总结是**工作流规则**，随项目走，不进全局 AGENTS.md（全局只留安全硬约束——小说等非代码项目不该被"验收命令/lint 门禁"刷噪音）。本机制：night-shift skill **首次进入某项目**时，把适配该项目类型的知识沉淀规则写进**该项目的 AGENTS.md**；之后每次进入只检查、不重复写。

## 一、初始化机制（agent 执行）

**时机**：进入夜班模式、写预检单（`preflights/<日期>.md`）之前（与 SKILL.md 主流程第 0 步并列）。

**幂等检查**：读工作区根 `AGENTS.md`（不存在则创建），查找标记：

```
<!-- night-shift-knowledge:v0 项目类型=<type> 初始化于=<date> -->
```

- **标记已存在** → 跳过初始化，检查 `项目类型=` 是否与当前判断一致；不一致（如中途从代码项目变成纯写作目录）→ 不自动改写，在简报"待拍板"里提示用户重初始化。
- **标记不存在** → 在文件末尾**追加"指针块"**（**不是全文复制**；文件已有内容一字不动，只追加，这是硬规则）。

**注入内容 = 指针块**（约 10 行，规则正文留在 skill 单一真源，见 §三/§四）：

```markdown
<!-- night-shift-knowledge:v0 项目类型=<code|noncode> 初始化于=<YYYY-MM-DD> -->

## 知识沉淀（night-shift）

- 本项目适用 night-shift 知识沉淀规则 **v0**（项目类型：<代码项目|非代码项目>）。
- **规则正文（唯一真源）**：`~/.dsh/skills/night-shift/references/project-init.md` §三 模板 A（非代码项目用 §四 模板 B）。
- **集中通用层**：`<centralKnowledge>`（由主机级 `config.json` 提供，默认 `$DSH_HOME/night-shift/central-knowledge`）。
- **项目差量**（本项目特有、覆盖通用规则的部分，可留空）：<如特殊验收命令、特殊目录约定>
```

> 指针形态的理由（用户 2026-10-30 定稿）：规则改一次全项目生效，不会出现"十个项目各躺一份旧版 v0"的漂移。代价：多一层间接、依赖 skill 安装路径稳定——所以**初始化时把解析后的绝对路径写进指针**，并在 BRIEF 回显"已加载指令文件清单"（§六-10）验证真的读到了。

**项目类型判定**（按目录特征，拿不准就问或按代码项目处理）：

| 类型 | 特征 | 用哪套规则正文（指针指向） |
|---|---|---|
| 代码项目 | `package.json` / `pyproject.toml` / `Cargo.toml` / `.csproj` / `go.mod` / `*.sln` 等清单文件，或有 src/tests 目录 | **§三 规则正文 A：代码项目**（全量五件套 + 验收命令 + 硬门禁回流） |
| 写作/知识项目 | `*.md` 为主、无构建清单（小说、笔记、文档仓库） | **§四 规则正文 B：非代码项目**（字段语义适配，无验收/lint 条目） |
| 混合/拿不准 | 两者特征都有 | 指针指向 A，并在"项目差量"里注明删去 `【代码专属】` 条目；实在拿不准 → 记入简报问用户，首次先不注入 |

**初始化后**：向用户报告一句话（"已注入知识沉淀**指针** v0（类型：代码），规则正文在 skill 内单一真源"）；夜班首晚把标记行 + 指针解析后的绝对路径抄进 BRIEF"预检执行情况"区。

**模板升级**：标记的 `v0` 随规则迭代递增（v1、v2…）。**指针形态下升级不用改项目文件**——改 skill 里的规则正文即可全项目生效；只有"项目类型判定变了"或"指针指向变了"才需要重写指针块。发现旧版本标记 → 简报提示"指针 v0→v1"，用户点头后只替换标记段落。

**主机级依赖（项目初始化只检查、不安装）**：本初始化**不做**看门狗/调度/运行登记表——那些是主机能力，装一次全局唯一，见 `host-level.md`。初始化时**读 `$DSH_HOME/night-shift/config.json` 的 `hostSetup` 块**：`subagentModel.configured=true` → 子代理模型已配，跳过；`watchdog.installed=true` → 看门狗已装，跳过；未配/未装 → 预检单提示并给对应 OS 的安装命令（Windows / macOS 各一条），等用户执行。**跨 OS 可移植**：模板里不写死绝对路径，集中通用层一律用 `<centralKnowledge>` 占位（由 `config.json` 提供，默认 `$DSH_HOME/night-shift/central-knowledge`）。

## 二、知识沉淀三层结构（2026-10-30 定稿：原始层 / 派生层 / 通用层）

> 设计来源：用户"数据清洗前保留原始数据"原则 + 借鉴用户 `docs/archive` 的归档实践（日期前缀文件 + "归档前全量"快照 + 主文件留"移出→路径+日期+裁定"指针注记）。核心纪律：**归并与提炼只产派生/通用层，永不改写、删除原件；退役用状态标记，不用删除；允许按年整体归档迁移**（§六-8）。

### 三层与流向

| 层 | 位置 | 性质 | 产生方式 |
|---|---|---|---|
| **原始层** | 项目内 `knowledge/{summaries,pitfalls,research}/` + `night-shift/{summaries,briefs,preflights,evidence,DECISIONS,ESCALATION}` | **append-only**：日期前缀，**永不改写、永不删除**；**允许按年整体归档迁移**（移到 `archive/<年>/`，文件名与目录结构不变，索引保留，见 §六-8）——数据清洗前的源数据 | 每任务/每晚自动产生 |
| **派生层** | 项目内 `knowledge/patterns/` | 可编辑（归并去重），但**每次编辑留痕**，每条带出处指针 → 原始层具体文件 | 提炼 pass（项目内扫描） |
| **通用层** | 集中 `<centralKnowledge>`（跨项目） | 可编辑，每条带**准入标记 + 出处链**（哪几个项目的哪几份原件）；退役 = 标 `refuted + 日期 + 证据指针`，**条目不删** | 提炼 pass（跨项目扫描） |

### 准入门槛（管预防——通用层的错误会污染所有项目）

一条经验进派生层/通用层，必须**同时**满足：

1. **≥2~3 次独立出现**——"独立"= **不同项目**，或**间隔 ≥7 天的不同任务**；同一任务链/同一篇总结里记三遍不算；
2. **根因确认一致**——表象相似但病因不同的**分开保留**（"项目A的 useEffect 卡顿"与"项目B的 useEffect 状态不同步"是两个条目）；
3. **"换个项目还成立"测试**——项目特定约定永远留在原始层，不上架；
4. **带出处链**（指回原始层具体文件）——无出处不上架。

> 门槛管**预防**（别让错的上架），原始层管**恢复**（上架后发现错的能回溯到原件修正）——两者互补，不可互替。

### 消费优先级（防拿到矛盾信息）

- 查阅顺序：**派生层/通用层优先**（提炼的意义就是不为用一条规则翻全部原件）；
- 与原始层冲突时：以**带最新状态标记的条目为准**，按出处链下钻核验；
- `status: refuted` 的条目仍可读（供追溯"为什么曾相信它"），但**不得作为决策依据**。

### 提炼 pass（执行动作——"写完之后单独分析抽离"的落点）

节奏：**月度**，与 skill 库月度维护（落地清单修订 3）同批。逐条扫各项目原始层的新总结/坑/决策，每条问三句：

① 第二个任务/项目遇到过同款吗？② 根因相同吗？③ 换个项目还成立吗？

- 三条全过 → 派生层（项目内）/ 通用层（跨项目，需 ≥2 项目来源），写出处链，记入集中库 `extraction-log.md`；
- 任一条不过 → 原件留在原始层，**不上架**；
- 已上架被后续证据推翻 → 状态改 `refuted` + 证伪证据指针，**条目不删**；
- **新项目初始化时先检索集中通用层**，适用条目作为开工调研第 0 步——这就是"新项目不从零开始"的实现。

## 三、规则正文 A：代码项目（由指针引用，不直接注入项目文件）

```markdown
## 知识沉淀（night-shift 规则正文 v0 · 代码项目）

### 开工前调研（新项目 / 新功能必做）

动手写码之前先调研：

1. **先查通用**：集中通用层 `<centralKnowledge>`（跨项目已提炼的经验，新项目不从零开始的入口）。
2. **再查内部**：`knowledge/research/` 已有调研笔记、`knowledge/pitfalls/` 相关踩坑、本项目 README/文档。
3. **再查外部**：GitHub / 社区 / 官方文档有无现成实现、轮子、最佳实践。**目的不是抄，是避免重新发明和重新踩坑**。
4. **落记录**：结论（参考链接 + 采纳与否一句话理由）记入任务总结"引用来源"；没找到也要写"查过 X、Y，无现成方案"——**"未调研"和"调研过没有"是两回事**。
5. **限 ~10 分钟无果** → 记入简报"待拍板/存疑"，按最合理假设推进，不整晚卡在调研上（夜班无人可问）。
6. **豁免**：修 bug、纯文档、用户已指定实现方式的任务，跳过外部调研（踩到新坑仍走"任务后总结"）。

### 任务后总结（每个实质任务一份）

- **要写**：改了代码行为 / 修了 bug / 搭了新功能 / 重要技术决策 / 踩了新坑。
- **不用写**：答疑、纯文字回复、一行 typo、用户明说"不用记录"的。
- **位置（原始层，append-only 按日期留档，永不改写/移动/删除）**：夜班 → `night-shift/summaries/<日期>-<任务短名>.md`；日常 → `knowledge/summaries/<日期>-<任务短名>.md`。归并/提炼只写 `knowledge/patterns/`（派生层），**不动原件**。
- **五件套**：任务与结果 / 踩过的坑（怎么错的怎么修的）/ 更好的实现方式 / 可复用片段【代码专属：含验收命令】/ 引用来源。
- **红线**：没跑过的测试不写"通过"；没查的来源不填链接——写错的总结比没有更害人。五件套允许写"无"，但"更好的实现方式"至少 1 条具体句（写不出说明这任务不该写总结）。

### 知识回流（让总结被用上，否则等于没写）

- 开工调研第 2 步**必须**查本项目 `knowledge/`——写进去没人查 = 白写。
- 【代码专属】同一坑/模式在总结里出现 ≥3 次 → 提议升级为硬门禁（lint 规则 / 验收脚本一条检查），走正常审批。
- 跨项目通用的条目 → **不直接上架通用层**，攒到月度提炼 pass 过准入门槛（≥2~3 次独立出现 + 根因一致 + 换项目成立 + 带出处）再进 `<centralKnowledge>`；原件永远在原始层。
- 相关 skill 的 description 里写明"先读 knowledge/pitfalls/"触发条件（按实际 skill 名替换）。
```

## 四、规则正文 B：非代码项目（由指针引用，不直接注入项目文件）

```markdown
## 知识沉淀（night-shift 规则正文 v0 · 非代码项目）

### 开工前调研（新主题 / 新章节 / 新设定必做）

动笔/动手之前先查：

1. **先查通用**：集中通用层 `<centralKnowledge>`（跨项目已提炼经验）。
2. **再查内部**：本项目 `knowledge/` 相关笔记、已有章节/文档是否已写过相关内容（防重复设定、防人设/时间线冲突）。
3. **再查外部**：同类作品、参考资料、权威文档有无可借鉴处。
4. **落记录**：结论记入任务总结"引用来源"；查过没有也要写"查过 X 无"。限 ~10 分钟无果 → 记简报按假设推进。

### 任务后总结（每个实质任务一份）

- **要写**：新增了设定/大纲改动 / 修了前后矛盾（坑）/ 形成了可复用的写法或结构 / 重要情节决策。
- **不用写**：答疑、单段润色、用户明说"不用记录"的。
- **位置（原始层，append-only 按日期留档）**：夜班 → `night-shift/summaries/<日期>-<任务短名>.md`；日常 → `knowledge/summaries/<日期>-<任务短名>.md`；归并提炼只写 `knowledge/patterns/`，不动原件。
- **五件套（语义适配）**：任务与结果 / 踩过的坑（设定矛盾、走偏的教训）/ 更好的写法或组织方式 / 可复用片段（可复用的写法、结构模板、常用资料）/ 引用来源。
- **红线**：与原文不符的"总结"不写；没查的引用不填链接。五件套允许写"无"，但"更好的写法/组织方式"至少 1 条具体句。

### 知识回流

- 开工调研第 2 步**必须**查本项目 `knowledge/`（已有人设表/设定集先对一遍再动笔）；第 1 步查集中通用层。
- 同类矛盾出现 ≥3 次 → 提议固化为检查清单（如"章前对照人设表"）；跨项目通用的条目走月度提炼 pass 过门槛后才进集中库，原件留原始层。
```

## 五、knowledge/ 目录骨架（初始化时顺带创建，已存在则跳过）

```
<项目>/knowledge/
├── research/    # 原始层·开工调研笔记（一主题一篇，append-only）
├── pitfalls/    # 原始层·踩坑档案（append-only）
├── summaries/   # 原始层·日常任务总结（夜班的在 night-shift/summaries/；append-only）
├── patterns/    # 派生层·归并后的模式（可编辑但留痕，每条带出处指针 → 原始层文件）
└── README.md    # 层级说明（原始/派生区分）+ 三行索引 + 最近更新
```

**集中通用层**（跨项目，月度提炼 pass 写入）：`<centralKnowledge>`（主机级 `config.json` 配置，默认 `$DSH_HOME/night-shift/central-knowledge`；Win `~\.dsh\...` / Mac `~/.dsh/...`）——完整结构与准入规则见《夜班流水线落地清单》§2.3 定稿 + 本文件 §二。

非代码项目可省 `research/`（并入 pitfalls 也行）——拿不准就不建，简报里问。**任何层级调整都只加新目录、不迁移旧文件**；唯一例外是 §六-8 的**年度整体归档**（只按年整目录迁移，不改文件名与内部结构，索引保留）。
